（2）① 加框处为什么执行 3 次
3 次
  1. 加框处统计while内排序代码块的执行轮数，不是交换语句次数。
  2. D 满足 30+80=110>100，属于无效任务，会不断向后交换。
  3. 第一趟中：D 和 E 交换 1 次，随后 D 和 F 再交换 1 次。
  4. 此时局部次序变成 ... E F D，但 E 的上传时刻 40 大于 F 的 30。
  5. 下一趟 E 和 F 再交换 1 次。
  6. 第三趟仍执行加框代码，交换0次，flag保持True，随后结束。
  7. 各轮交换2、1、0次，总计3轮；累计交换也恰好为3次，两者含义不同。
（2）② return 为什么填 i
return i
  1. retain 前半部分已经把“能在 time 前完成的任务”放在前面，把无效任务放在后面。
  2. 后面的二分就是在找这两部分的分界位置。
  3. 若 a[mid][1] + a[mid][2] > time，说明 mid 无效，要去左边找，因此 j = mid - 1。
  4. 否则 mid 有效，要继续向右找，因此 i = mid + 1。
  5. 循环结束后，i 恰好指向第一个无效任务的位置。
  6. 因为下标从 0 开始，所以“第一个无效任务的下标”正好等于“有效任务个数”。
有效任务：0 ... i-1 无效任务：i ... n-1 所以返回有效任务数：return i
（3）① 为什么是完成时刻
now = a[i][1] + a[i][2]
  1. 进入这一分支的关键条件是 h == -1：当前没有等待任务。
  2. 同时 a[i][1] >= now：下一个任务还没上传，或者恰好现在上传。
  3. 因此计算机可能需要先空等到 a[i][1] 时刻。
  4. 任务真正开始时刻是它的上传时刻，执行 a[i][2] 个时间单位。
  5. 所以新的 now 必须是：上传时刻 + 所需时长。
开始时刻 = a[i][1] 完成时刻 = a[i][1] + a[i][2]
（3）② 为什么是 a[i][1] <= now
a[i][1] <= now
  1. 这一整个 elif 分支的作用不是执行任务，而是：把已经上传的任务加入等待链表。
  2. 一个任务只要“上传时刻不晚于当前时刻 now”，就已经可以等待。
  3. 因此条件自然是 a[i][1] <= now。
  4. 等号不能少：例如 E 恰好在 A 完成的 now=40 时上传。
  5. 如果只写 <，E 在 40 时刻就不会及时进入等待链表，后续选择顺序会出错。
（3）③ 为什么是 a[i][3] = p
a[i][3] = p
  1. 这里是在把新任务 i 插入一个按“所需时长升序”排列的单链表。
  2. 循环结束后：q 指向插入位置前一个结点，p 指向插入位置后一个结点。
  3. 原来的连接关系是：q → p。
  4. 插入 i 后要变成：q → i → p。
  5. 程序已经写了 a[q][3] = i，完成了 q → i。
  6. 还必须补上 i → p，所以：a[i][3] = p。
插入前：q → p 插入后：q → i → p 已有：a[q][3] = i 还缺：a[i][3] = p
